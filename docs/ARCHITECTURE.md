# Local architecture

The React/TypeScript/Vite client uses React Query for saved server state, Radix dialog/tooltip primitives and a lazily loaded ECharts line chart. Navigation and chart interactions do not execute calculations. The production build is served by FastAPI on loopback. A separate Python worker reads a persistent SQLite queue. No Streamlit or v1 code is used.

`python -m aperture` starts API + worker and stops its child on shutdown. One worker per database is enforced with an OS file lock. On worker startup, interrupted running jobs are marked failed with an actionable explanation; queued jobs continue. Identical active task requests deduplicate. Progress is persisted. Result insertion and job completion share one transaction, so a failed computation cannot publish a partial result. SQLite uses WAL and transactions; schema v1 is recorded explicitly. Future schema changes need ordered migrations.

The API validates bounded request bodies and strategy/data availability. Mutations require a custom same-origin client header; CORS is not enabled. Trusted hostnames and loopback binding narrow the local boundary. This is not an authenticated multi-user/hosted application. Do not expose it publicly before the hosting/security milestone.

The database stores compressed immutable dataset bodies, compressed submitted UTF-8 source content, captured provider responses, task payloads and saved results. Schema v2 adds observations and local watchlist preferences. Application data and local environment files are ignored by Git. Paper credentials are read privately for historical data and paper-only broker operations. Schema v3 adds frozen protocols/trials and paper approvals/plans/orders/events. Schema v4 adds compressed immutable membership captures and their original source payloads; `membership.py` resolves current or historical rosters, bounded coverage and decision eligibility. `broker.py` fixes order writes to the paper host; `paper.py` handles approvals, preparation, bounded execution and reconciliation. No live adapter exists. Dependency versions are locked in `uv.lock` and `web/package-lock.json`.

The core domain is independent of the HTTP layer: `signals.py` controls historical observation cutoffs, `portfolio.py` constructs constrained targets, `ledger.py` handles corporate actions and simulated fills, and `metrics.py` calculates display-window statistics. Both backtests and read-only reviews use the same strategy definitions and target construction. Paper planning uses the same strategy/target policy, adding account identity, actual positions, conservative spendable cash, asset eligibility, live quote bounds, approval/version checks and durable client identifiers.

`providers.py` bounds/caches official HTTP reads and archives responses. `fundamentals.py` normalizes annual statements by accession, period, unit and filing availability, and enriches a price snapshot without mutating it. Signal code combines only eligible components; results carry filing audits, exclusions and parent/source fingerprints. Current issuer directories and fixed watchlists remain explicit historical-identity limitations.

The worker also checks paper state on a bounded local loop. Only explicit approved manual plans or matching automatic permissions can reach submission. It persists a client identifier before a single HTTP write attempt; ambiguous outcomes are looked up, never blindly retried. Order records survive worker interruption and remain separate from interrupted read-only jobs. `account_performance.py` retains broker daily equity/activities in a private account-specific archive and computes explicitly labelled end-of-day cash-flow-adjusted estimates. Page navigation reads saved state and never contacts the broker. See [paper contract](PAPER_TRADING.md).
